# 工作计划：在职状态档位与优先级策略

## 核心前提

用户是**在职员工，工作日上班时间不可学习**。因此学习计划不能全窗口使用同一个每日学时：
工作日只安排下班后的少量时间，周末集中补进度。排期按「日历天」分别取容量，而不是
`daily_hours × days` 这种均匀假设。

## 工作状态档位（`tobacco.py profile`）

| 档位 | 中文 | 工作日学时 | 周末学时 | 适用 |
| --- | --- | --- | --- | --- |
| `office`（默认） | 在职坐班 | 1.0 | 3.0 | 工作日白天在岗，仅晚间可学 |
| `overtime` | 加班 / 出差旺季 | 0.5 | 2.0 | 工作日几乎不可学 |
| `leave` | 休假 / 脱产培训 | 4.0 | 4.0 | 全周可集中学习 |
| `shift` | 轮班制 | 1.5 | 1.5 | 作息不固定，保守安排 |
| `flat` | 统一每日学时 | 2.0 | 2.0 | 不区分工作日与周末 |

周末 = `date.weekday() >= 5`（周六、周日）。配置持久化在 `data/profile.json`，
未配置时回落 `office` + `layered`。

```bash
# 查看
python scripts/tobacco.py profile get --json

# 设置（换档会重置该档内置学时，随后可用覆盖参数微调）
python scripts/tobacco.py profile set --work-profile office \
    --weekday-hours 1 --weekend-hours 3 \
    --priority layered --note "工作日上班时间不可学习"

# 恢复默认
python scripts/tobacco.py profile reset
```

`plan` 的参数覆盖顺序（后者优先）：已保存档位 → `--work-profile` → `--weekday-hours` /
`--weekend-hours` → `--daily-hours`（显式给出即视为 `flat` 统一档，兼容旧用法）→ `--priority`。
临时覆盖**不会**写回 `profile.json`。

端到端工作流模板见 `@//templates/workflow.sh`。

## 优先级策略

用户要求「**必修优先、临期优先**」。旧算法里必修只有 +180，会被「3 天内截止」的 800 分
碾压，等于没有必修优先。现在提供三种策略，默认 `layered`：

| 策略 | 必修加权 | 行为 |
| --- | --- | --- |
| `layered`（默认） | +800 | 必修常态优先；**今天/明天截止的选修 +350 可插队抢救** |
| `required-first` | +10000 | 必修严格优先：所有必修排完才排选修，组内按临期 |
| `deadline-first` | +180 | 按截止日优先，必修只在同日打破平局（近似旧行为） |

临期基础分保留原梯度：逾期 880（+3/天）、今天 980、明天 920、3 天内 800、
5 天内 650、7 天内 560、10 天内 430、20 天内 270、更远 150、无截止 120；
另有密度加权（≤120）、类型加权（考试 120 / 直播 90 / 班级 60 / 课程 40 / 问卷 20）、
未完成进度加权（≤60）。

### layered 的实际效果（冲突样例）

| 任务 | 必修 | 截止 | 主要得分 | 排位 |
| --- | --- | --- | --- | --- |
| 线上综合考核 | 是 | 今天 | 980 + 800 + 120 | 1 |
| 临时安全测验 | 否 | 明天 | 920 + 350(插队) + 120 | 2 |
| 合规专题 | 是 | 57 天后 | 150 + 800 + 40 | 3 |
| 选修：数据分析 | 否 | 3 天后 | 800 + 40 | 4 |

取舍说明：
- **必修常态压过非紧急选修**（3 天后截止的选修排在两个必修之后）；
- **只有今天/明天截止的选修允许插队**，避免"为了两个月后的必修课而错过明天的考试"；
- **逾期任务不给插队加成**，保留"逾期已是既成事实、临期尚可挽救"的原设计；
- 逾期靠 +3/天 递增，长期不处理会重新浮到前面。

用户明确要"必修绝对优先"或"临期绝对优先"时，用 `--priority` 切换，并说明切换后
可能出现的后果（例如必修绝对优先会把明天到期的选修压后）。

## 排期约束（不变）

- 未到期任务**绝不排到自己的截止日之后**；已逾期任务不受截止日约束，尽快补完。
- 容量不足时产生 `overflow`，并区分「截止日前容量不足」与「超出计划窗口」。
- 提示语按档位给出：建议提高 `--weekday-hours` / `--weekend-hours` 或延长 `--days`，
  不再笼统说"把每日学时提到 X"。
- 输出每天标注 `工作日 / 周末` 与 `已排 / 当日容量` 学时，空档日也显示容量。

## 与学时缺口的关系

任务排完**不等于**年度考核达标。平台学时缺口（如集中培训差 26 学时）来自
`@//references/task-api.md` 的学时总览，是年度要求，不等于任何单条任务的 `hours`。
每次呈现计划时都要单独提示缺口，不要把它硬塞进任务时长。

## 线下集中培训是固定日程，不进每日容量

`credit_group=集中培训` 的任务（班级，businessType=5）是**线下形式**：
有固定起止（班级详情接口的 `startTime`/`endTime`）、固定学时（`classHour`）和地点，
只能现场参训，**不能**拆成"每晚 1 学时"，也不占每日自学容量。`build_plan` 会把它们
单列为计划里的「线下集中培训（固定日程）」区块，并在 7 天内要结束时给出警告；
每日安排只放网络自学的课程。两组学时独立考核，网课补不了集中培训的缺口。

## 已知数据边界

平台不返回逐任务进度百分比；除班级外多数任务也不返回 `duration`，`hours` 是按类型估的
（课程 2.0 / 直播 1.5 / 考试 1.0 / 问卷 0.2 学时；班级取详情接口真实 `classHour`）。
因此每日学时与计划总学时可能是估算，向用户汇报时要说明。
